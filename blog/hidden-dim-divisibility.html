The Hidden Dimension Divisibility Problem

Here's a constraint violation I find in roughly 40% of custom architectures I evaluate. It's simple to understand, easy to miss, and catastrophically expensive to discover during training.

The Math

In a transformer, your hidden dimension (d_model) must satisfy a specific relationship with your attention heads and head dimension. Specifically:

d_model % num_heads == 0
d_model % head_dim == 0
num_heads * head_dim == d_model

Seems obvious when you see it. Here's where it breaks down in practice.

The Common Mistake

A team decides on these specs:

  • d_model = 2048
  • num_heads = 16
  • head_dim = 128

Looks fine. 16 * 128 = 2048. But wait—128 isn't divisible by anything sensible in many implementations. Some frameworks require head_dim to be a power of 2, or to divide evenly into 64.

Or they do:

  • d_model = 3072
  • num_heads = 24
  • head_dim = 128

24 * 128 = 3072. Correct math. But what if your attention implementation requires num_heads to divide d_model evenly across all GPU threads? Now you're in trouble.

Real Example

One engagement: d_model=8192, num_heads=64, head_dim=128. The architecture was supposed to match Llama-2's specs.

Problem: Their custom CUDA kernel only supported head_dim in {32, 64, 128}. They had 128, so it should work, right? Wrong. The kernel required head_dim * num_heads to fit in shared memory. 128 * 64 = 8192 bytes, but their GPU only had 8192 bytes of shared memory per block, leaving zero room for other variables.

Training would run for 10-20 minutes, then hit a CUDA out-of-memory error that looked like a batch size problem. They spent 2 weeks trying to reduce batch size before they called me.

How ArchGene Catches This

We model the constraints as SMT (Satisfiability Modulo Theories) formulas using Z3. Given your architecture parameters, we ask: does there exist a valid execution path that satisfies all constraints?

For the divisibility constraint:

(declare-const d_model Int)
(declare-const num_heads Int)
(assert (= (mod d_model num_heads) 0))
(check-sat)

If this returns "unsat", your architecture can never work, regardless of implementation quality.

The Checklist

Before committing to training, verify:

  • d_model divisible by num_heads
  • d_model divisible by head_dim (if specified)
  • num_heads * head_dim == d_model
  • head_dim is a power of 2 (for most efficient implementations)
  • head_dim >= 64 (smaller heads often indicate architectural issues)
  • d_model >= num_heads (yes, I've seen this violated)

The Cost

Catching this before training: $0 (using ArchGene or reading this post).

Catching it during training: $10K-$100K in wasted compute.

Catching it in production: Your model's outputs are subtly wrong and you don't know why.

The Point

Dimension divisibility is basic math. But in complex systems, basic math becomes easy to miss. Formal verification exists precisely for this—catching the obvious problems that obvious gets lost in the noise.
